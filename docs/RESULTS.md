# GaugeVision — Results

Numbers here are produced by the actual implemented code (see the command
that generated each section) — never a plausible-sounding figure copied from
memory or a paper without checking the specific table/metric/protocol it came
from (CLAUDE.md §4.3, §8, §10).

## Anomaly detection — PaDiM baseline (Phase 1)

Generated by `python -m gaugevision.anomaly.train`.

- Backbone: frozen ResNet18 (ImageNet weights), layers 1–3, concatenated at
  layer2's spatial resolution (28×28) — see `anomaly/padim.py` for the
  CPU-feasibility rationale.
- Random feature selection: 100 dims (fixed seed).
- Fit on 320 defect-free "screw" training images (MVTec AD).
- Threshold: 99th percentile of the *training* (normal-only) score
  distribution — chosen without looking at test labels, so the AUROC below
  is a clean held-out evaluation, not one where the threshold was tuned
  against the test set.

| Metric | Value |
|---|---|
| Test set (n=160) image-level AUROC | **0.7569** |
| n normal / n anomalous in test set | 41 / 119 |
| Fitted threshold (train p99.0, normal-only scores) | 14.7987 |

Reproduce with `python -m gaugevision.anomaly.train` (fixed seed=0).

**Comparison against published PaDiM results (CLAUDE.md §4.3 — image-level,
not pixel-level, AUROC; specific backbone confirmed):** the PaDiM paper
(Defard et al., 2020, arXiv:2011.08785) reports **0.745** image-level AUROC
on MVTec "screw" for the **R18-Rd100** configuration — ResNet18 backbone,
random dimensionality reduction to 100 features — which is exactly this
project's configuration (`n_features=100`, ResNet18). Source: the paper's
per-category table as reproduced in the widely-cited unofficial
implementation [xiahaifeng1995/PaDiM-Anomaly-Detection-Localization-master](https://github.com/xiahaifeng1995/PaDiM-Anomaly-Detection-Localization-master)
(the same source also lists screw pixel-level AUROC as 0.972 for R18-Rd100 —
confirmed distinct from the 0.745 image-level figure, so the two aren't
conflated here). This project's measured **0.7569** is within ~1.2 points of
that published number under a matched backbone/feature-dim configuration —
a reasonable reproduction, not an exact match (different random seed for the
100-feature subset, different train/test image ordering).

## Anomaly detection — PatchCore (Phase 4 stretch)

Generated by `python -m gaugevision.anomaly.train_patchcore`.

- Reuses the **same** frozen ResNet18 + multiscale-concat feature extractor
  as the PaDiM baseline above (`PaDiMBackbone`) rather than a separately
  tuned backbone — see `anomaly/patchcore.py` for why: this isolates the
  comparison to "distribution modeling (PaDiM) vs. memory-bank +
  nearest-neighbor (PatchCore)" on identical features, rather than mixing in
  backbone differences.
- Memory bank: 250,880 total patches (320 train images × 784 patches) →
  random-subsampled to a 20,000-patch candidate pool → greedy k-center
  (farthest-point) coreset selection down to 2,000 points.
- Same threshold methodology as PaDiM (99th percentile of training-only
  scores) for a fair comparison.

| Metric | Value |
|---|---|
| Test set (n=160) image-level AUROC | **0.7208** |
| Memory bank size | 2,000 (from 250,880 total patches) |
| Fitted threshold (train p99.0) | 2.7268 |

**PatchCore underperformed PaDiM in this implementation** (0.7208 vs
0.7569) — worth documenting why rather than hiding it (CLAUDE.md §8, §10).
The published PatchCore paper (Roth et al., 2022, arXiv:2106.08265, CVPR
2022) reports **0.987** image-level AUROC on MVTec "screw", but with a
**WideResNet50** backbone and PatchCore's own local-aggregation feature
extraction (blocks 2-3, average-pooled), not the ResNet18 +
PaDiM-style-multiscale-concat features this implementation deliberately
reuses for a controlled PaDiM comparison. The gap versus that published
number is therefore expected and not a claim that this PatchCore
implementation is broken — it's a smaller-scope reproduction sharing this
project's own PaDiM backbone, not a reproduction of the paper's best-in-class
setup (larger backbone, purpose-built patch aggregation, larger memory
bank). A backbone-matched PatchCore vs PaDiM comparison (both on
WideResNet50) is future work, not done here — see CLAUDE.md §11's open
question on whether PatchCore was worth pursuing at all; it was, and the
answer this implementation gives is "PaDiM remains the better choice for
this project's config," which is why PaDiM stays the model behind the live
API rather than PatchCore.

## Measurement pipeline validation (Phase 4)

Generated by `gaugevision.measurement.validate` against
`data/synthetic_thread.py` samples with known ground-truth dimensions — see
that module's docstring for why synthetic ground truth is necessary (MVTec
AD has no physical scale reference at all). Calibration for this validation
uses `MetricCalibration.synthetic_reference` — **validated within this
harness only**; real MVTec image inference still uses the Phase-1
`demo_reference` source, since MVTec photos contain no physical reference
object to calibrate against (see that classmethod's docstring for the full
reasoning — applying the synthetic scale to real MVTec pixels would
fabricate a number with no relationship to those photos' actual scale).

Sweep: 3 thread sizes (M3, M6, M10, reusing the ISO 965 starter table's basic
dimensions) × 3 conditions (clean / Gaussian blur / 20° in-plane rotation) ×
2 pitch estimators = 18 cases.

**Major diameter** (identical for both estimators — diameter estimation
doesn't depend on which pitch estimator is used):

| Condition | Diameter MAE (mm) | Mean % error |
|---|---|---|
| Clean | 0.0500 | 1.00% |
| Blur | 0.0333 | 0.72% |
| Rotated | 0.1000 | 1.50% |

**Pitch — PeakPitchEstimator vs FFTPitchEstimator comparison table**
(CLAUDE.md §4.2's requested table shape), with estimate-coverage noted since
MAE alone hides a reliability difference between the two:

| Method | Clean pitch MAE (mm) | Blur pitch MAE (mm) | Rotated pitch MAE (mm) |
|---|---|---|---|
| FFTPitchEstimator | 0.0014 (3/3 produced an estimate) | 0.0005 (3/3 produced an estimate) | 0.0080 (3/3 produced an estimate) |
| PeakPitchEstimator | 0.0000 (3/3 produced an estimate) | 0.0000 (3/3 produced an estimate) | 0.0000 (1/3 produced an estimate) |

Reproduce with:
```python
from gaugevision.measurement.validate import run_validation_sweep, summarize, format_pitch_comparison_table
records = run_validation_sweep()
print(format_pitch_comparison_table(summarize(records)))
```

**Reading this table, and the default-estimator decision it drives:**
`PeakPitchEstimator` has essentially perfect precision (0.0000mm MAE)
whenever it produces an estimate, but its coverage drops to 1/3 under
rotation (find_peaks needs ≥3 well-formed prominent peaks; a rotated,
resampled signal sometimes doesn't have them). `FFTPitchEstimator` has
100% coverage across every condition, with small but nonzero error that
grows under rotation (0.008mm MAE, still under 1% of the 1-1.75mm pitches
tested) — a genuinely more robust estimator **on clean synthetic ground
truth where the signal actually contains real periodicity**.

That "on synthetic ground truth" qualifier is load-bearing. Repeating the
same PeakPitchEstimator-vs-FFTPitchEstimator comparison against 15 real
MVTec test images (not synthetic) — where Phase 1 already established the
width-profile signal is dominated by the screw's taper, not genuine
thread-crest periodicity (see the README's Known Limitations) — flips the
conclusion:

| Method | Real MVTec coverage | Real MVTec behavior |
|---|---|---|
| PeakPitchEstimator | 0/15 | Correctly reports "no reliable estimate" (confidence 0, `pitch_px=None`) every time — `find_peaks` honestly can't find ≥3 well-formed peaks in a taper-dominated signal. |
| FFTPitchEstimator | 15/15 | Always reports a pitch estimate **with confidence 1.00**, but the values are wildly inconsistent across visually similar screws (32px to 178px) — the detrended residual signal is dominated by segmentation noise, not real periodicity, and FFT always has *some* dominant frequency bin to report. Confidence does not correlate with correctness here. |

This is the single most important finding CLAUDE.md §8 asked this
validation to surface ("confirm the confidence flag actually correlates
with higher error when it fires") — and the honest answer is: **it does
for PeakPitchEstimator, and it does not for FFTPitchEstimator, on real
degraded images.** A confidently-wrong estimate is worse for a QC decision
system than an honest "I don't know," so **PeakPitchEstimator remains the
pipeline's deployed default** despite losing the synthetic-only coverage
comparison — this is a case where the "pick the default from evidence"
instruction (CLAUDE.md §4.2) means picking the estimator whose *failure
mode* is safe on the actual target data, not the one with the better
synthetic-only numbers. `FFTPitchEstimator` remains available behind the
same `PitchEstimator` interface, and is more accurate when the input signal
is genuinely periodic (as the synthetic table above shows) — the limiting
factor is upstream profile extraction on real images, not either
estimator's own algorithm; see the README's Known Limitations for that.

**Bug found and fixed during this validation:** `isolate_thread_region`
(`measurement/profile.py`) computed its head-exclusion margin as a fraction
of the *whole derotated frame length*, not the part's own foreground extent.
This was invisible in Phase 1's own unit tests (where the synthetic screw
nearly filled its canvas) but produced a measured diameter equal to the
screw's *head* width (not the thread crest width) whenever there was
background margin around the part — exactly the scenario this validation
harness's more realistic canvas layout exposed. Fixed to compute the margin
relative to the foreground's own row extent; see the function's updated
docstring for the general fix and `tests/test_synthetic_thread.py` /
`tests/test_measurement_pipeline.py` for regression coverage.

## ONNX / inference optimization benchmark (Phase 2)

Generated by `python -m gaugevision.deployment.export_onnx` then
`python -m gaugevision.deployment.benchmark`.

**Scope note (CLAUDE.md §4.4):** only the PaDiM backbone (frozen ResNet18
feature extraction + multiscale concat, `PaDiMBackbone`) is exported to ONNX.
PaDiM's Gaussian-distribution Mahalanobis scoring stays in NumPy and runs
identically on top of either backend's extracted features — this is the
documented backbone/scoring split CLAUDE.md explicitly allows, since PaDiM's
scoring logic doesn't translate cleanly through the ONNX exporter. The
benchmark below measures the actual shipped architecture: backbone in
PyTorch-or-ONNX-Runtime, scoring in NumPy either way — not a full-pipeline
ONNX claim.

**Hardware/config context** (these numbers are machine-specific, not a
general PyTorch-vs-ONNX-Runtime claim): Apple Silicon, macOS, arm64. PyTorch
used its default 4 intra-op threads; ONNX Runtime used its default
auto-detected thread count (`intra_op_num_threads=0`) on the
`CPUExecutionProvider`. Neither was hand-tuned — this is an "out of the box"
comparison.

| Metric | PyTorch (CPU) | ONNX Runtime (CPU) |
|---|---|---|
| Backbone artifact size | 11,180,149 B (state_dict) | 11,133,529 B |
| Cold start | 1013.8 ms | 886.1 ms |
| Mean latency / image | 16.28 ms | 17.76 ms |
| p50 latency | 16.18 ms | 17.58 ms |
| p95 latency | 16.84 ms | 19.41 ms |
| Throughput | 61.4 img/s | 56.3 img/s |
| Peak process RSS | 431.7 MB | 423.9 MB |

Latency/throughput/memory measured over 50 timed iterations (5 warmup) on a
fixed 400×400 synthetic image, each backend run in its own subprocess so
peak RSS is attributable to one backend at a time.

**Output equivalence** (20 real MVTec "screw" test images, PyTorch vs ONNX
Runtime image-level anomaly score): max absolute diff **1.00×10⁻⁵**, max
relative diff **6.10×10⁻⁷**, well within the defined tolerance
(atol=1e-2, rtol=1e-3) — **passed**. The exported ONNX graph reproduces the
PyTorch model's output to within floating-point noise.

**Honest finding, not the expected direction:** ONNX Runtime CPU was *not*
faster than PyTorch CPU for this small backbone on this machine — PyTorch
was ~9% faster on mean latency, though ONNX Runtime had a ~13% faster cold
start. This is a real, reproducible result on Apple Silicon arm64 with both
runtimes at default thread settings, not a benchmark bug: PyTorch's CPU
kernels are already well-optimized on this platform for a model this small,
and the theoretical benefits of graph optimization / operator fusion in ONNX
Runtime are more pronounced on larger models, batched inference, or x86
targets with oneDNN acceleration — none of which apply directly here.
Reported here rather than suppressed, per CLAUDE.md §10's "prefer honest,
benchmarked numbers over polished claims" — the ONNX export path is still
valuable for portability (running outside the PyTorch runtime, e.g. the
Phase 6 C++ edge demo) even without a CPU latency win on this specific
hardware/model combination.

Reproduce with:
```bash
python -m gaugevision.deployment.export_onnx
python -m gaugevision.deployment.benchmark
```

## Video pipeline (Phase 3)

Not a benchmark section like the ones above — video input reuses the exact
same measurement/anomaly/decision functions the image endpoint calls
(`run_measurement_pipeline`, `PaDiM.predict`, `fuse_verdict`), per frame, so
its accuracy is whatever those already-benchmarked components produce. What
was actually verified end-to-end (`POST /inspect/video`, both directly and
through the Gradio UI, against `gaugevision/video/pipeline.py`):

- A 10-second, 100-frame test video assembled from 10 real MVTec "screw" test
  images (5 normal, 5 defective) was submitted to `/inspect/video`.
- Frame sampling at the default ~2 samples/sec (interval derived from source
  FPS) produced 50 sampled frames; **measured inspection throughput ~52
  frames/sec** — consistent with the per-image PyTorch CPU latency in the
  Phase 2 benchmark above (~16ms/frame), since video inspection is that same
  per-frame call in a loop, not a separate optimized path.
- Worst-case temporal aggregation (`NO_GO` if any sampled frame fails a
  check) correctly flagged the assembled video `NO_GO` with both
  `anomaly_score` and `major_diameter` in `overall_failed_checks`, matching
  the per-frame verdicts.
- The annotated output video (heatmap blended in, verdict/anomaly/diameter/
  pitch/FPS/failed-checks text overlaid) was decoded and visually inspected
  frame-by-frame — overlays render legibly and match the JSON verdict for
  that frame.
- `tests/test_video_pipeline.py` covers frame-sampling-interval math and the
  orchestration (aggregation, output-video writing, the
  measurement-pipeline-failure fallback) against a synthesized video, since
  MVTec AD has no video assets of its own.

No dimensional-accuracy or defect-detection-rate claim is made for video
specifically — that's inherited entirely from the Phase 1/2 measurement and
anomaly-detection numbers above, with the same limitations (notably: pitch
estimation not firing reliably on real screw images, see the README's
Known Limitations section).

## C++ edge-inference demo (Phase 6)

Generated by building and running `edge/cpp/` (see `edge/cpp/README.md` for
build instructions) against real MVTec "screw" test images, compared to the
Python `PaDiM` class's score for the same images.

**Scope note:** this is deliberately a minimal proof that inference works
outside the Python runtime (CLAUDE.md §4.8), not a rigorously isolated
benchmark like the Phase 2 ONNX Runtime comparison (no subprocess isolation,
no warmup-then-percentile methodology, small sample size). Preprocessing
also isn't bit-identical to the Python path — OpenCV's bilinear resize and
PyTorch's `F.interpolate` bilinear resize use different implementations —
so scores are expected to be *close*, not identical, unlike the Phase 2
Python-vs-ONNX-Runtime comparison (which shared the exact same preprocessing
code and matched to ~1e-5).

| Image | Python score | C++ score | Abs diff | Rel diff |
|---|---|---|---|---|
| 002-86.png | 14.5524 | 14.5618 | 0.0094 | 0.064% |
| 002-83.png | 14.6511 | 14.5670 | 0.0841 | 0.574% |
| 016-61.png | 14.4326 | 14.5093 | 0.0767 | 0.531% |
| 017-51.png | 16.4616 | 16.3539 | 0.1077 | 0.654% |
| 003-83.png | 12.5412 | 12.5806 | 0.0394 | 0.314% |

Mean absolute diff: **0.0635**. Max: 0.1077. Mean relative diff: **0.43%**.
Max: 0.65%. Small, consistent with the documented preprocessing difference,
and stable across repeated runs on the same image (scores were
bit-for-bit identical across repeated invocations on the same input,
confirming the C++ path itself is deterministic).

**Latency:** steady-state single-image latency (preprocess + ONNX Runtime
inference + Mahalanobis scoring, wall time) measured 17-25ms across repeated
runs — consistent with the Phase 2 Python ONNX Runtime CPU benchmark
(~17.76ms mean). A few individual runs measured 160-170ms instead; these
coincided with heavy background system activity (a large Homebrew install
had just completed on this machine) rather than a property of the C++ code
itself — reported honestly rather than cherry-picking only the fast runs,
but not treated as the demo's characteristic latency given the confound.

Reproduce:
```bash
python -m gaugevision.deployment.export_onnx         # if not already run
python -m gaugevision.deployment.export_cpp_stats
cmake -S edge/cpp -B edge/cpp/build && cmake --build edge/cpp/build
./edge/cpp/build/gaugevision_edge_demo models/padim_backbone.onnx models/padim_stats_cpp.bin <image_path>
```
